*説明
Leeyesをユニコードのファイル名に対応させるプログラム一式

*動作環境
Windows7の64bitで確認
XP対応のビルドだが動作未確認

*使用方法
Leeyes本体のフォルダに以下のファイルをコピー
 LeeyesW.exe	:DLLインジェクション用プログラム
 inject_dll.dll	:SHBindToParent,CreateFileAのフックDLL
 inject_dll.ini	:設定ファイル

このセットに含まれない以下のファイルをLeeyesで利用できる位置に配置
Ax7z.dll	:書庫プラグイン本体 Ax7z_s.dll等の他のプラグインを利用する場合はiniを書き換え
7z.dll		:Ax7z.dllに必要

オリジナルのLeeyesが起動していないのを確認した後LeeyesW.exeで起動
プラグイン設定でAx7z.dllの優先度を一番上にするか他のチェックを外して
ユニコードを含むフォルダや書庫、画像ファイルが開ければ成功

Leeyesの設定でファイラ:一覧:「書庫内はサブフォルダの内容も表示する」にチェック入れるのを推奨


*制限事項
 OSの設定やドライブの種類で短いパスを利用できないようにしてあると書庫ファイルが開けない
普通の設定でも場合により短いパスが存在しない事もある

 Leeyesで表示上のUnicode文字が [?] に変更され見た目で重複している場合は片方しか読めない事もある
（例：abc?ef.jpgが2つあるが実際は [?] が別のUnicode文字の個別のファイル)

 全ての名前のファイルが読めるようになるわけではない

 本棚にUnicodeのファイルを登録すると開けなくなる

 アドレスバーにUnicodeを含むパスを入れても開けない

 削除、名前の変更、プロパティ等が使えない

*既知の不具合
 ユニコードを含む名前の書庫ファイルがツリー上で重複してしまう事がある。アドレスが別名として表示される

 マウスホイール等で移動していると次のファイルを見失いツリーが正しい位置に移動しない事がある


*動作原理
Leeyesの関数呼び出しをフックしてパス取得時に変換できない文字が含まれている場合に
8.3形式の短いパスに入れ替えでマルチバイト用のファイルAPIを正常動作させる
変なアンチウィルスソフトは過剰反応しそうなのでソースコードも添付

*ソースコード
Visual Studio 2012でビルド
ライセンスはソースに記載のあるのはそれに従う
それ以外はPDSらしい
プラグインは未実装の機能が多いので実装してくれて公開されると嬉しい

*2026年 現行Windows環境向け修復について(改修時追記)

以下を実施し、Visual Studio 2022 / 現行Windows 10-11 環境でも動作するように修復した。
 - Src.7z内のVisual Studio 2012 (v110_xp) ソリューションをVS2022 (v143) 向けに移植
   (相対includeパスの解決、標準ヘッダの明示的include追加。フック対象APIや
   フォールバックロジック等の既存挙動は変更していない)
 - LeeyesW.exeのDLL注入方式を変更
   従来はIATを書き換えて偽の追加インポートをローダーに読み込ませる方式だったが、
   現行Windowsのローダーはこの偽インポートを無視するようになっており、
   inject_dll.dllが読み込まれないまま無効化されていた。
   変更後: プロセスを通常起動し、CreateRemoteThread + LoadLibraryW で
   inject_dll.dllを注入する方式に変更(フック対象・タイミングは実質的に同じ)。

*WSL(Windows Subsystem for Linux)導入環境での既知の問題と対応(解消済み)

WSLをインストールした環境では、ネットワークプロバイダの優先順位
(レジストリ HKLM\SYSTEM\CurrentControlSet\Control\NetworkProvider\Order) の
先頭に P9NP (\\wsl$ アクセス用プロバイダ) が入る。
この状態でinject_dll.dllをLeeyes.exeに注入すると、起動直後に限らず、
フォルダ移動などシェル関連の操作をした際にもLeeyesがクラッシュすることがあった
(P9NP内部の不具合が誘発される。エラーコード0xE06D7363)。
特にOSを長期間再起動していない環境ほど発生しやすい(調査時、5ヶ月以上
再起動していない環境ではほぼ100%再現した)。

当初はレジストリのP9NPを一時的に取り除く管理者権限必須のランチャーで
回避していたが、根本原因を追って以下の対策をinject_dll.dll自体に実装し、
管理者権限なしで解消した(このプロセス内だけの対応で、システム全体の
設定は一切変更しない)。
 - p9np.dllがこのプロセスに読み込まれること自体をブロック
   (kernel32!LoadLibrary系、ntdll!LdrLoadDllをフック)
 - このプロセスがレジストリの NetworkProvider\Order を読み取る際、
   P9NPをこのプロセスの目には見えないよう除外して返す
   (RegQueryValueExWをフック。レジストリ自体への書き込みは一切行わない)

これにより LeeyesW.exe を普通に(管理者権限なしで)起動するだけで、
P9NP関連のクラッシュは発生しなくなった。同梱の Launch_Leeyes_Unicode.bat/.ps1 は
現在は不要(このフォルダに残してあるが使わなくてよい)。

*絵文字等、サロゲートペアを含む文字について

CP932(Shift-JIS)で表現できない文字(絵文字、一部のCJK拡張漢字、他言語の文字等)は
Leeyesの一覧上では [?] として表示されるが、実際のファイルアクセスには
8.3短縮パスへのフォールバックが使われるため、フォルダ名・画像・書庫の展開は
正常に行える(2014年のオリジナル設計通りの動作)。
